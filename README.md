دستور merge دو شاخه را با هم ترکیب می‌کند. گیت نقطهٔ مشترک دو شاخه را پیدا می‌کند و تغییرات هر دو را ادغام می‌کند و معمولاً یک کامیت جدید به اسم merge commit می‌سازد که دو والد دارد. کامیت‌های قبلی دست نمی‌خورند و تاریخچه همان‌طور که واقعاً اتفاق افتاده باقی می‌ماند، یعنی انشعاب‌ها و محل به هم پیوستن شاخه‌ها در گراف دیده می‌شود.
دستور rebase کامیت‌های شاخهٔ فعلی را برمی‌دارد و یکی‌یکی روی آخرین کامیت شاخهٔ دیگر دوباره اعمال می‌کند. محتوای تغییرات همان است ولی کامیت‌ها hash جدید می‌گیرند. نتیجه یک تاریخچهٔ خطی و مرتب است، انگار کار از اول روی آخرین نسخهٔ شاخهٔ اصلی انجام شده. پس merge تاریخچه را حفظ می‌کند و rebase آن را بازنویسی می‌کند. یک فرق دیگر این است که در merge تعارض‌ها یک‌جا حل می‌شوند ولی در rebase ممکن است برای هر کامیت جداگانه حل شوند.
موقعیت مناسب برای merge وقتی است که کار یک قابلیت روی یک شاخهٔ مشترک تمام شده و چند نفر روی آن کامیت زده‌اند و حالا باید وارد شاخهٔ main شود. اینجا merge را انتخاب می‌کنم چون شاخه بین چند نفر مشترک است و اگر rebase شود hash کامیت‌ها عوض می‌شود و کار بقیه به هم می‌ریزد. علاوه بر این، merge commit نشان می‌دهد این قابلیت کی وارد شده و در صورت مشکل می‌شود کل آن را یک‌جا برگرداند.
موقعیت مناسب برای rebase وقتی است که روی شاخهٔ شخصی خودم کار می‌کنم که هنوز push نکرده‌ام و در این مدت main چند کامیت جدید گرفته است. اینجا با rebase شاخه‌ام را روی آخرین نسخهٔ main می‌برم، چون شاخه فقط مال خودم است و بازنویسی تاریخچه به کسی ضرر نمی‌زند. این‌طوری تاریخچه پر از کامیت‌های merge بی‌معنی نمی‌شود و وقتی شاخه را برای بررسی می‌فرستم، تاریخچه‌اش تمیز و خطی است.
