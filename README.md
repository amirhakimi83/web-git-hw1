## سوال ۱

دستور merge دو شاخه را با هم ترکیب می‌کند. گیت نقطهٔ مشترک دو شاخه را پیدا می‌کند و تغییرات هر دو را ادغام می‌کند و معمولاً یک کامیت جدید به اسم merge commit می‌سازد که دو والد دارد. کامیت‌های قبلی دست نمی‌خورند و تاریخچه همان‌طور که واقعاً اتفاق افتاده باقی می‌ماند، یعنی انشعاب‌ها و محل به هم پیوستن شاخه‌ها در گراف دیده می‌شود.

دستور rebase کامیت‌های شاخهٔ فعلی را برمی‌دارد و یکی‌یکی روی آخرین کامیت شاخهٔ دیگر دوباره اعمال می‌کند. محتوای تغییرات همان است ولی کامیت‌ها hash جدید می‌گیرند. نتیجه یک تاریخچهٔ خطی و مرتب است، انگار کار از اول روی آخرین نسخهٔ شاخهٔ اصلی انجام شده. پس merge تاریخچه را حفظ می‌کند و rebase آن را بازنویسی می‌کند. یک فرق دیگر این است که در merge تعارض‌ها یک‌جا حل می‌شوند ولی در rebase ممکن است برای هر کامیت جداگانه حل شوند.

موقعیت مناسب برای merge وقتی است که کار یک قابلیت روی یک شاخهٔ مشترک تمام شده و چند نفر روی آن کامیت زده‌اند و حالا باید وارد شاخهٔ main شود. اینجا merge را انتخاب می‌کنم چون شاخه بین چند نفر مشترک است و اگر rebase شود hash کامیت‌ها عوض می‌شود و کار بقیه به هم می‌ریزد. علاوه بر این، merge commit نشان می‌دهد این قابلیت کی وارد شده و در صورت مشکل می‌شود کل آن را یک‌جا برگرداند.

موقعیت مناسب برای rebase وقتی است که روی شاخهٔ شخصی خودم کار می‌کنم که هنوز push نکرده‌ام و در این مدت main چند کامیت جدید گرفته است. اینجا با rebase شاخه‌ام را روی آخرین نسخهٔ main می‌برم، چون شاخه فقط مال خودم است و بازنویسی تاریخچه به کسی ضرر نمی‌زند. این‌طوری تاریخچه پر از کامیت‌های merge بی‌معنی نمی‌شود و وقتی شاخه را برای بررسی می‌فرستم، تاریخچه‌اش تمیز و خطی است.

## سوال ۲

در خروجی `git diff`، تغییرات یک فایل به چند تکه تقسیم می‌شود که به هر تکه hunk می‌گویند. هر hunk یک قسمت پیوسته از فایل است که تغییر کرده، همراه با چند خط اطرافش برای اینکه معلوم باشد تغییر کجای فایل است. هر hunk با سرخطی مثل `@@ -12,5 +12,7 @@` شروع می‌شود که می‌گوید این بخش در نسخهٔ قبلی از خط ۱۲ و به طول ۵ خط بوده و در نسخهٔ جدید از خط ۱۲ و به طول ۷ خط است. خط‌هایی که با `-` شروع می‌شوند حذف شده‌اند و خط‌هایی که با `+` شروع می‌شوند اضافه شده‌اند.

برای اینکه تغییرات یک فایل را تکه‌تکه ببینیم و فقط بعضی را stage کنیم از این دستور استفاده می‌کنیم:

<div dir="ltr">

```bash
git add -p file.py
```

</div>

(`-p` همان `--patch` است.) گیت hunkها را یکی‌یکی نشان می‌دهد و برای هر کدام می‌پرسد چه کار کند. پاسخ‌های اصلی این‌ها هستند:

- `y` این hunk را stage کن
- `n` این hunk را stage نکن
- `s` این hunk را به hunkهای کوچک‌تر تقسیم کن (وقتی چند تغییر جدا از هم در یک hunk افتاده‌اند)
- `e` hunk را دستی ویرایش کن تا فقط خط‌های دلخواه stage شوند
- `a` این hunk و بقیهٔ hunkهای این فایل را stage کن
- `d` این hunk و بقیهٔ hunkهای این فایل را stage نکن
- `q` خارج شو
- `?` راهنمای گزینه‌ها

بعد از انتخاب‌ها با `git diff --cached` می‌شود دید دقیقاً چه چیزی stage شده و با `git diff` می‌شود دید چه چیزی هنوز بیرون مانده. بعد کامیت می‌کنیم:

<div dir="ltr">

```bash
git diff --cached
git commit -m "..."
```

</div>

اگر چیزی را اشتباهی stage کرده باشیم، با `git restore --staged -p file.py` می‌شود به همین شکل تعاملی آن را از staging بیرون آورد.

فایدهٔ این کار این است که خیلی وقت‌ها در یک فایل چند کار مختلف انجام می‌دهیم، مثلاً یک باگ را درست می‌کنیم و هم‌زمان کمی کد را مرتب می‌کنیم یا یک قابلیت جدید را شروع می‌کنیم. با `add -p` می‌توانیم این تغییرات را از هم جدا کنیم و هر کدام را در کامیت جداگانه بگذاریم. این‌طوری هر کامیت فقط یک کار مشخص انجام می‌دهد، پیامش دقیق است، بررسی‌اش برای بقیه راحت‌تر است و اگر لازم شد می‌شود فقط همان یک تغییر را revert یا cherry-pick کرد بدون اینکه بقیهٔ تغییرات هم برگردند.

## سوال ۳

دستور `git bisect` با جست‌وجوی دودویی کامیتی را پیدا می‌کند که یک خطا را وارد کرده است. ما یک کامیت سالم که خطا در آن نبوده و یک کامیت معیوب که خطا در آن هست را مشخص می‌کنیم. گیت کامیت وسط این بازه را checkout می‌کند و ما آن را تست می‌کنیم. با هر جواب، نصف بازه حذف می‌شود و این کار تا وقتی ادامه پیدا می‌کند که فقط یک کامیت باقی بماند.

مراحل کار این‌طور است:

<div dir="ltr">

```bash
git bisect start
git bisect bad
git bisect good v1.2
```

</div>

بعد از این، گیت کامیتی در وسط بازه را checkout می‌کند. برنامه را اجرا یا تست می‌کنیم و نتیجه را اعلام می‌کنیم:

<div dir="ltr">

```bash
git bisect good
git bisect bad
```

</div>

اگر کامیتی به دلیل دیگری قابل تست نبود، مثلاً build نمی‌شد، با `git bisect skip` از آن رد می‌شویم. این مرحله چند بار تکرار می‌شود تا گیت پیغام بدهد کدام کامیت اولین کامیت معیوب است و مشخصاتش را نشان دهد. در آخر با `git bisect reset` به شاخه و وضعیت قبل از شروع برمی‌گردیم.

اگر تستی داشته باشیم که بتواند خودکار تشخیص بدهد خطا هست یا نه، می‌شود کل کار را به گیت سپرد:

<div dir="ltr">

```bash
git bisect run ./test.sh
```

</div>

خروجی صفر یعنی سالم و خروجی غیرصفر یعنی معیوب، و گیت خودش تا پیدا کردن کامیت مقصر جلو می‌رود.

مثال: فرض کنید در یک سامانه، صفحهٔ گزارش‌ها تا نسخهٔ v2.0 درست کار می‌کرده ولی الان بعد از حدود ۲۰۰ کامیت، جمع مبالغ اشتباه نشان داده می‌شود و معلوم نیست کدام تغییر باعثش شده. bisect را شروع می‌کنیم، کامیت فعلی را bad و v2.0 را good اعلام می‌کنیم. در هر مرحله صفحهٔ گزارش را باز می‌کنیم و جمع را چک می‌کنیم. بعد از حدود ۸ مرحله گیت کامیتی را نشان می‌دهد که مثلاً نحوهٔ گرد کردن اعداد را تغییر داده بود، و با دیدن diff همان کامیت علت خطا معلوم می‌شود.

این روش مفید است چون به‌جای بررسی تک‌تک کامیت‌ها، در هر مرحله نصف کامیت‌ها کنار می‌روند. برای ۲۰۰ کامیت حدود ۸ تست و برای ۱۰۰۰ کامیت حدود ۱۰ تست کافی است. همچنین لازم نیست از قبل بدانیم خطا در کدام قسمت کد است، چون فقط بر اساس رفتار برنامه جلو می‌رویم. در نهایت به یک کامیت مشخص می‌رسیم که diff کوچکی دارد و پیدا کردن علت در آن خیلی راحت‌تر از گشتن در کل کد است. این کار وقتی بهتر جواب می‌دهد که کامیت‌ها کوچک و منسجم باشند.

## سوال ۴

۱. برای دیدن وضعیت کلی مخزن از `git status` استفاده می‌کنم. در این حالت README.md هم زیر «Changes to be committed» و هم زیر «Changes not staged for commit» دیده می‌شود، چون بخشی از تغییراتش stage شده و بخشی نه. پوشهٔ tmp هم زیر «Untracked files» نشان داده می‌شود.

برای دیدن تغییراتی که هنوز stage نشده‌اند از `git diff` استفاده می‌کنم. این دستور پوشهٔ کاری را با ناحیهٔ staging مقایسه می‌کند، پس فقط ویرایش‌هایی را نشان می‌دهد که بعد از آخرین `git add` انجام داده‌ام.

برای دیدن تغییرات آمادهٔ کامیت از `git diff --staged` (یا `git diff --cached`) استفاده می‌کنم. این دستور ناحیهٔ staging را با آخرین کامیت (HEAD) مقایسه می‌کند، یعنی دقیقاً همان چیزی را نشان می‌دهد که اگر الان کامیت کنم وارد کامیت می‌شود.

پس تفاوت این دو دسته در این است که تغییرات unstaged فقط در پوشهٔ کاری هستند و هنوز به staging نرفته‌اند، ولی تغییرات staged در ناحیهٔ staging ثبت شده‌اند و در کامیت بعدی قرار می‌گیرند.

۲. اگر الان `git commit` بدون `-a` بزنم، فقط تغییراتی از README.md وارد کامیت می‌شود که قبلاً با `git add` به staging رفته بودند. ویرایش‌هایی که بعد از آن انجام دادم داخل کامیت نیستند و بعد از کامیت همچنان به‌صورت modified و unstaged در پوشهٔ کاری باقی می‌مانند. دلیلش این است که `git add` یک نسخه از محتوای فایل در همان لحظه را در staging ذخیره می‌کند و کامیت از روی همین نسخهٔ ذخیره‌شده ساخته می‌شود، نه از روی فایل فعلی در پوشهٔ کاری. ویرایش‌های بعدی تا دوباره add نشوند روی staging اثری ندارند. فایل‌های داخل tmp هم چون untracked هستند وارد کامیت نمی‌شوند.

۳. در فایل `.gitignore` در ریشهٔ مخزن این خط را اضافه می‌کنم:

<div dir="ltr">

```
/tmp/
```

</div>

اسلش اول یعنی فقط پوشهٔ tmp در ریشهٔ مخزن، و اسلش آخر یعنی این الگو برای پوشه است. بعد خود `.gitignore` را کامیت می‌کنم تا این تنظیم برای بقیهٔ اعضای تیم هم اعمال شود. (اگر بخواهم فقط روی سیستم خودم اعمال شود، می‌توانم همین خط را در `.git/info/exclude` بنویسم.)

این تنظیم برای فایلی که قبلاً tracked شده کافی نیست. `.gitignore` فقط روی فایل‌های untracked اثر دارد و جلوی اضافه شدن آن‌ها را می‌گیرد، ولی گیت تغییرات فایلی را که از قبل در مخزن هست همچنان دنبال می‌کند. برای چنین فایلی اول باید آن را از ناحیهٔ staging و از دنبال‌شدن خارج کنم، بدون اینکه از دیسک پاک شود:

<div dir="ltr">

```bash
git rm --cached -r tmp/
git commit -m "Stop tracking tmp folder"
```

</div>

بعد از این، فایل در پوشهٔ کاری باقی می‌ماند ولی دیگر tracked نیست و `.gitignore` از اضافه شدن دوباره‌اش جلوگیری می‌کند.

## سوال ۵

۱. چون هر دو شاخه از یک کامیت مشترک شروع کرده‌اند و هر کدام یک خط را به متن متفاوتی تغییر داده‌اند، گیت نمی‌تواند تصمیم بگیرد کدام نسخه درست است. هر تغییری در یک فایل لزوماً conflict ایجاد نمی‌کند. اگر تغییرات در قسمت‌های جدا از هم فایل باشند، گیت خودش آن‌ها را ادغام می‌کند. conflict فقط وقتی پیش می‌آید که خط‌های یکسان یا نزدیک به هم به دو شکل متفاوت تغییر کرده باشند.

۲. با `git status` فایل‌های درگیر زیر «Unmerged paths» و با عنوان `both modified` دیده می‌شوند. داخل فایل، گیت دو نسخه را این‌طور مشخص می‌کند:

<div dir="ltr">

```
<<<<<<< HEAD
متن main
=======
متن description-feature
>>>>>>> description-feature
```

</div>

بالای `=======` نسخهٔ شاخهٔ فعلی و پایینش نسخهٔ شاخهٔ merge‌شده است. این علامت‌ها فقط محل conflict را نشان می‌دهند و باید پاک شوند.

۳. فایل را باز می‌کنم، دو متن را طوری ترکیب می‌کنم که اطلاعات هر دو حفظ شود و markerها را پاک می‌کنم. برای اطمینان از اینکه markerی نمانده از این دستور استفاده می‌کنم:

<div dir="ltr">

```bash
git diff --check
```

</div>

بعد merge را تمام می‌کنم:

<div dir="ltr">

```bash
git add README.md
git commit
```

</div>

۴. با دستور زیر merge لغو می‌شود و مخزن به وضعیت قبل از merge برمی‌گردد:

<div dir="ltr">

```bash
git merge --abort
```

</div>

## سوال ۶

۱. با این دستور تغییرات notes.txt دور ریخته می‌شود:

<div dir="ltr">

```bash
git restore notes.txt
```

</div>

(در نسخه‌های قدیمی‌تر: `git checkout -- notes.txt`.) این دستور فایل را در working tree از روی نسخهٔ ناحیهٔ staging بازنویسی می‌کند. چون staging با آخرین کامیت یکسان است، فایل به حالت آخرین کامیت برمی‌گردد. staging، تاریخچه و بقیهٔ فایل‌ها تغییری نمی‌کنند. تغییرات دورریخته‌شده قابل بازیابی نیستند.

۲. با این دستور فایل از staging خارج می‌شود:

<div dir="ltr">

```bash
git restore --staged notes.txt
```

</div>

(یا `git reset notes.txt`.) این دستور نسخهٔ فایل در staging را به نسخهٔ آخرین کامیت برمی‌گرداند. ویرایش‌ها در working tree باقی می‌مانند و فایل دوباره به‌صورت modified و unstaged نشان داده می‌شود. تاریخچه تغییری نمی‌کند.

۳. روش مناسب استفاده از revert است:

<div dir="ltr">

```bash
git revert <hash>
git push
```

</div>

این دستور یک کامیت جدید می‌سازد که دقیقاً برعکس تغییرات کامیت اشتباه است. working tree و staging بعد از revert با نتیجهٔ جدید یکی می‌شوند و در تاریخچه هم کامیت اشتباه و هم کامیت برگرداننده باقی می‌مانند.

حذف کامیت با reset و بعد `push --force` مناسب نیست، چون هم‌تیمی‌ها آن کامیت را دریافت کرده‌اند و تاریخچهٔ آن‌ها با سرور ناهماهنگ می‌شود. در نتیجه موقع pull به مشکل می‌خورند و ممکن است کامیت حذف‌شده دوباره وارد شود یا کارهایی که روی آن انجام داده‌اند از بین برود. revert تاریخچه را بازنویسی نمی‌کند و هم‌تیمی‌ها فقط با یک pull معمولی آن را دریافت می‌کنند.
